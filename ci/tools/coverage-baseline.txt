# WHY THE DIFF IS THIS SMALL, PER nginx-module-testkit's docs/COVERAGE.md
# authority ("Where coverage is measured, and where it is not"):
#
#   That policy states coverage is a UNIT-BUILD measurement and explicitly
#   NOT one taken through a booted nginx, because booting mixes module lines
#   with nginx core lines and attributes work to whichever request happened
#   to land -- and it says the prober/scenario suite's actual value (leak
#   neutrality, lifecycle survival, fault-path behaviour) is DELIBERATELY NOT
#   a coverage claim.
#
#   This module's own ci/tools/coverage.sh already diverges from that: it is
#   ALSO a booted-nginx gcov measurement (test_runtime.py driving a real
#   instrumented server), a repo-level decision made before this file existed.
#   The prober legs measured here extend that same booted-nginx methodology
#   rather than violating a unit-build-only policy this repo never adopted.
#   The two measurements are consistent in kind; what they are NOT is
#   additive with each other in the way a unit-build report would be, because
#   both are "whichever code the request path happened to touch" -- so a
#   large chunk of what ci/tools/coverage.sh's OWN suite already exercises on
#   the same real HTTP paths (config merge, HIT/MISS, vary, filters) is
#   necessarily already covered before the prober legs run at all. Nine
#   incremental lines is a small, structurally-expected number given that the
#   two measurements share a code surface, not a sign the harness under-ran.
