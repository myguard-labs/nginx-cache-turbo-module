# P4-2-s3c — BLOCKED, escalated before any code change

Status: no source change. This branch carries the analysis only.

## Why s3c cannot be implemented as scoped

Two facts, both verified against `main` @ 8f01167:

1. **No call site is key-directed.** `ngx_http_cache_turbo_stripe_of()` has
   ZERO callers outside its own definition comment
   (`grep -rn ngx_http_cache_turbo_stripe_of src/` matches only the header
   definition and a prose reference in shm.c:97). All ~276 pool/sh/mutex
   dereferences go through the ZONE-WIDE resolver
   (`zone_sh()` / `zone_pool()` / `zone_mutex()`), which is hard-coded
   `&z->stripes[0]` and is NOT parameterised by key.

   Consequence: carving N pools produces 1 populated pool and N-1 permanently
   empty ones. The rbtree, both LRU queues, `n_entries`, `n_protected`, every
   counter and `used_bytes` all live in `stripes[0].sh`. Nothing routes to
   stripes 1..N-1 because nothing asks `stripe_of()`.

   `N=4 boots, serves, purges` would pass — but only because N=4 is
   behaviourally identical to N=1 plus wasted shm. The done criterion is
   satisfiable without the feature working, i.e. it is vacuous.

2. **Porting call sites to `stripe_of()` is exactly s3d, which is GATED.**
   Making stripe 1..N-1 reachable means giving each stripe its own rbtree +
   LRU + `n_entries`, and then PURGE-by-tag, the autotune recompute, the
   breaker and the admin aggregate all become cross-stripe fan-outs. The
   packet forbids all of that ("do not port PURGE-by-tag, the LRU /
   lru_protected queues, n_entries/n_protected accounting, autotune, or
   shm_admit()") and forbids ever holding two stripe mutexes.

## The used_bytes clause is the same conflict

Constraint 4 requires `used_bytes` to AGGREGATE across stripes and the admin
surface to show a per-stripe breakdown. Under fact 1 the aggregate is
identically `stripes[0].sh->used_bytes` and every other stripe reports 0
forever. `shm.c:1067/1084` charge and discharge through `zone_sh()`, so there
is no per-stripe number to aggregate. Implementing the aggregate loop now
ships an admin field that is guaranteed-constant-zero for N-1 of N stripes —
an operator-facing lie, which constraint 4 exists to prevent.

## Secondary (not the blocker, but unresolved by the packet)

nginx hands the module ONE `ngx_slab_pool_t` at `shm_zone->shm.addr` for the
whole zone (`ngx_shared_memory_add` + `shm_zone->init`, conf.c:1579-1590).
Carving N *independent* pools means sub-dividing that mapping by hand and
running `ngx_slab_init()` on each sub-range with its own mutex. That is a
real technique but it is a shm-layout decision with a reload/inheritance path
(`shm.exists` re-attach at shm.c:110, and the `octx` copy at 104-108 which
copies ONE stripe struct, not an array) and a minimum-viable zone size policy.
The packet's constraint 5 gestures at it ("reject an N whose per-stripe carve
cannot fit the zone size") but does not settle the layout or the floor.

Note also: `stripe_of()` indexes with `key % nstripes`, a MODULO, not a mask —
so a power-of-2 restriction is not currently forced by the resolver. That
sub-question of constraint 5 resolves as "no power-of-2 constraint needed"
if the modulo is kept.
